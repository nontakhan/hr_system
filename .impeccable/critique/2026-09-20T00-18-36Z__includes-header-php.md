บันทึกนี้เป็นผลตรวจก่อนปรับปรุง ดูรายการที่แก้แล้วและหลักฐานล่าสุดใน [รายงานแก้ UX เร่งด่วน](../../docs/audits/2026-09-20/urgent-ux-fixes.md)

การตรวจนี้เป็น expert review ตาม impeccable โดยผู้ช่วยสองตัวประเมินอิสระ แล้วตรวจหลักฐานซ้ำและสังเคราะห์ร่วมกับการไล่เส้นทาง page → JavaScript → API → helper ของผู้ตรวจหลัก ไม่ใช่ผลทดสอบ usability กับผู้ใช้จริง คะแนนหน้าภายในเป็นคะแนนเบื้องต้นจาก source เพราะเบราว์เซอร์ทดสอบยังไม่ได้ล็อกอิน ไม่มีการส่งคำขอ อนุมัติ เปลี่ยนข้อมูล หรือทดสอบสิทธิ์ด้วยบัญชีจริง

## ภาพรวมการออกแบบ

Sarabun, Bootstrap, เมนูพร้อมข้อความภาษาไทย และตารางข้อมูลเป็นภาษาการออกแบบที่เหมาะกับระบบนี้ ควรรักษาไว้ ความสม่ำเสมอมีประโยชน์กับงานประจำ ไม่ควรเปลี่ยนฟอนต์หรือทำหน้าตาใหม่ทั้งระบบเพราะ detector แจ้งเตือน

หน้าเข้าสู่ระบบมีการตกแต่งมากกว่าที่งานต้องใช้ ทั้งแสงเรือง ลายเฉียง และข้อความประชาสัมพันธ์ บนมือถือสิ่งเหล่านี้แย่งพื้นที่จากฟอร์มจริง เห็นผลชัดกว่าคำวิจารณ์ด้านรสนิยม: ที่ 390 × 844 ช่องชื่อผู้ใช้เริ่มประมาณ y=832 และปุ่มเข้าสู่ระบบอยู่ประมาณ y=1036

## สิ่งที่ทำได้ดี

2. **ฟอร์มลาอธิบายผลคำนวณ** แยกวันและชั่วโมง แสดงวันนับ/ไม่นับและจำนวนลา ช่วยลดการคำนวณเองของพนักงาน [ฟอร์ม](C:/xampp/htdocs/hr_system/leave_request.php:51)

## Flow ของแต่ละบทบาท

| บทบาท | เส้นทางที่ควรชัดที่สุด | ผลประเมินปัจจุบัน |
|---|---|---|
| พนักงาน | งานของฉัน → ประวัติคำขอ → สร้างคำขอ → ดูว่ารอใคร → ติดตาม/ขอยกเลิก | โครงสร้างหลักเข้าใจได้ แต่หน้า home แสดงสถานะไม่ครบและให้น้ำหนักเฉพาะการลา |
| หัวหน้างาน | งานรอฉันอนุมัติ → อ่านเหตุผล/วัน/จำนวน → ตัดสินใจ → ส่งต่อ HR | มีคิวตามขั้นอนุมัติและผู้ใต้บังคับบัญชา แต่ home เน้นสถิติจำนวนพนักงาน ส่วนกล่องยืนยันขาดรายละเอียดคำขอ |
| HR | งานในขอบเขตที่รับผิดชอบ → ตรวจคำขอ/เวลา → อนุมัติหรือทำแทน → ตรวจรายงาน | มีขอบเขตบริษัท/สาขาในหลายเส้นทาง แต่เมนูเวลาทำงานของพนักงานซ่อนอยู่ในหมวด “ของฉัน” และงานประจำปนการตั้งค่า |
| admin | ภาพรวม → งานที่ต้องจัดการ → บัญชีและสิทธิ์/ข้อมูลพื้นฐาน | ใช้พื้นที่งานคล้าย HR ขณะที่บัญชีและสิทธิ์อยู่ท้ายฟอร์มพนักงาน การระบุหน้าที่ของ “ข้อมูลพื้นฐาน” กับ “สิทธิ์ผู้ใช้” ยังไม่ชัด |

ข้อเท็จจริงของ flow ที่ควรสื่อให้ผู้ใช้เข้าใจ: คำขอปกติผ่านหัวหน้างานก่อน HR ส่วน “ทำรายการแทนพนักงาน” บันทึกและอนุมัติทันทีตามคำอธิบายและ API เดิม จึงควรแสดงชื่อพนักงานที่กำลังทำแทนให้เห็นชัดจนถึงตอนบันทึก [หน้าทำแทน](C:/xampp/htdocs/hr_system/request_proxy.php:75)

## ประเด็นเร่งด่วน

P1 หมายถึงทำให้เกิดความสับสนหรืออุปสรรคสำคัญ ควรแก้ก่อนรับรองความพร้อม ส่วน P2 เป็นการปรับรอบถัดไป ไม่มี P0 ที่พิสูจน์ว่าปิดกั้นระบบทั้งหมดในการตรวจรอบนี้

### 1. [P1] สถานะบน dashboard ไม่ตรงกับวงจรคำขอที่ใช้อยู่

คำขอใหม่ถูกบันทึกเป็น pending_manager แต่สรุป dashboard นับเฉพาะ pending, approved, rejected และ cancelled ทำให้รายการรอหัวหน้า/รอ HR ไม่ถูกรวมในยอดรออนุมัติ ส่วนตัวแสดง badge ไม่รู้จัก pending_manager, pending_hr และ pending_cancel_hr จึงแสดงชื่อสถานะภาษาอังกฤษดิบ

หลักฐาน: [สถานะที่บันทึก](C:/xampp/htdocs/hr_system/api/leave_request_api.php:186), [การนับบน dashboard](C:/xampp/htdocs/hr_system/api/dashboard_api.php:189), [ตัวแสดง badge](C:/xampp/htdocs/hr_system/assets/js/dashboard.js:74)

การเรียกตัวแสดง badge จริงด้วยข้อมูลสมมติผ่าน Node VM ยืนยันว่า pending_manager แสดงเป็น pending_manager และ pending_hr แสดงเป็น pending_hr โดยไม่ได้เชื่อมฐานข้อมูล

**ผลกระทบ:** พนักงานอาจเห็นยอดรออนุมัติเป็นศูนย์ทั้งที่คำขอยังอยู่ระหว่างดำเนินการ จึงไม่รู้ว่าคำขอส่งสำเร็จหรือควรติดต่อใคร

**แนวทาง:** ใช้กลุ่มสถานะและคำแปลร่วมกันกับหน้าประวัติ แสดง “รอหัวหน้างาน”, “รอ HR” และ “รออนุมัติยกเลิก” ให้ครบ รวมถึงเพิ่มสถานะโหลดล้มเหลวพร้อมปุ่มลองใหม่แทนการค้าง “กำลังโหลด...”

**คำสั่งที่เหมาะ:** $impeccable harden และ $impeccable clarify โดยต้องแก้สัญญา API และ UI ให้ตรงกันด้วย

### 2. [P1] การเข้าสู่ระบบและการกู้คืนยังมีทางตัน

ลิงก์ “ลืมรหัสผ่าน?” เป็น href="#" และการคลิกจริงไม่ได้เปิดขั้นตอนช่วยเหลือ นอกจากนี้โค้ด inline ปิด loginBtn ทุกครั้งที่ส่งฟอร์ม แต่ handler ที่โหลดจริงไม่มีการเปิดปุ่มกลับเมื่อเข้าสู่ระบบไม่สำเร็จหรือเครือข่ายล้มเหลว

หลักฐาน: [ลืมรหัสผ่าน](C:/xampp/htdocs/hr_system/index.php:396), [ปิดปุ่ม](C:/xampp/htdocs/hr_system/index.php:432), [handler ฝั่งล้มเหลว](C:/xampp/htdocs/hr_system/assets/js/login.js:44)

**ผลกระทบ:** คนที่เข้าระบบไม่ได้ไม่รู้ว่าจะทำอย่างไรต่อ พฤติกรรมปุ่มค้างยืนยันจาก source แต่ไม่ได้ทดลองส่งข้อมูลล็อกอิน

**แนวทาง:** ให้ handler เดียวดูแล loading และเปิดปุ่มกลับใน finally เมื่อไม่สำเร็จ คงชื่อผู้ใช้ไว้ เปลี่ยนลิงก์ช่วยเหลือเป็นขั้นตอนกู้คืนที่มีอยู่จริงหรือคำแนะนำติดต่อ HR/IT ที่ถูกต้อง

## ภาระในการคิดและความมั่นใจ

พบปัญหาหลัก 3 จาก 8 ด้านใน checklist: จุดสนใจหลักบน login มือถือไม่ชัด, ลำดับสายตาให้ความสำคัญกับเนื้อหารอง และผู้อนุมัติต้องจำบริบทของคำขอ ส่วนการจัดกลุ่มฟอร์มและเปิดข้อมูลตามโหมดทำได้ดี

เมนูคำขอมี 5 ประเภท (6 สำหรับ HR/admin), เมนูอนุมัติมี 5 ประเภท, กลุ่ม HR มี 8/9 รายการ ตัวเลขมากกว่า 4 ไม่ได้แปลว่าผิดโดยอัตโนมัติ ปัญหาคือความต่างของงานที่อยู่รวมกันและการเสียบริบท ไม่ใช่เพียงจำนวนเมนู

การเดินทางทางอารมณ์: ผู้ใช้ได้รับความมั่นใจจากผลคำนวณวันลาและข้อความสำเร็จ แต่ความมั่นใจลดลงเมื่อเข้าระบบไม่สำเร็จ เมื่อยอดรออนุมัติไม่ตรง และเมื่อกล่องยืนยันซ่อนรายละเอียดของสิ่งที่กำลังตัดสินใจ

## มุมมองผู้ใช้ที่ควรใช้ทดสอบต่อ

- **พนักงานใหม่:** เข้าระบบไม่ได้แล้วมีขั้นตอนช่วยเหลือจริงหรือไม่ ส่งคำขอแล้วรู้ว่ารอใครหรือไม่
- **ผู้ใช้คีย์บอร์ด/โปรแกรมอ่านหน้าจอ:** ระบุช่องวันที่และเวลาได้ไหม เปิดปิดเมนูและแสดงรหัสผ่านได้ไหม
- **พนักงานใช้มือถือ:** เข้าถึงฟอร์ม login ได้ทันที อ่านประวัติและปุ่มของแถวได้โดยไม่เลื่อนหาไปมาเกินจำเป็นหรือไม่
- **หัวหน้า:** อ่านเหตุผลเต็มและยืนยันคำขอที่ถูกคน ถูกวัน โดยไม่ต้องจำจากหน้าก่อนได้ไหม
- **HR/admin:** รู้ตลอดว่ากำลังทำรายการให้ใครและอยู่ในขอบเขตใด ปุ่มที่เห็นใช้งานได้ตามสิทธิ์จริงหรือไม่

## ผล detector และการเทียบกับการประเมินมนุษย์

CLI ประมวลผล PHP ที่ระบุชื่อไฟล์โดยตรง ได้ 3 warnings: em-dash-overuse ที่ generate_password.php:0 และ single-font ที่ index.php:22 กับ includes/header.php:83 ทั้งสามเป็น false positives สำหรับงานนี้: ตัวแรกจับเส้นคั่นใน comment ส่วนสองตัวหลังขัดกับหลัก product register ที่อนุญาตฟอนต์เดียว

เครื่องมือนี้ใช้ regex กับ PHP และไม่ได้ render หน้า authenticated จึงไม่ถือว่าพบเพียง 3 warnings แล้ว UX ผ่านทั้งหมด Wrapper รายงาน exit 1 แม้ implementation ใช้ exit 2 เมื่อมี findings; JSON ใช้งานได้ ไม่ใช่ detector crash

Browser overlay หน้า login พบ 6 findings ใน 5 rules: dark-glow 2, clipped-overflow-container 1, low-contrast 1, skipped-heading 1 และ repeating-stripes-gradient 1 จุด clipping ยังไม่มีหลักฐานว่าตัดตัวควบคุมสำคัญ จึงไม่นับเป็นปัญหายืนยัน ส่วน contrast, heading, ลายเฉียงและแสงเรืองตรงกับสิ่งที่ตรวจจากภาพ

ผู้ช่วยทั้งสองพบตรงกันเรื่องลืมรหัสผ่าน มือถือ และ accessible name ของปุ่มรหัสผ่าน ผู้ตรวจหลักพบเพิ่มเรื่องสถานะ dashboard และความสอดคล้องของสิทธิ์ตามเส้นทาง source
